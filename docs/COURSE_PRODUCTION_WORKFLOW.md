# 单课生产、编辑与审核工作流

适用于新课与既有教材精修。教学和中文以 [编辑规范 V1.0](COURSE_EDITORIAL_STANDARD_V1.md) 为标准，数据、组件、路由和发布按 [工程编写指南](COURSE_AUTHORING.md) 接入。两者均须满足；事实、先修与章节范围以 `curriculum/` 为准。原稿仍标记为规范草案，修订规范由维护者审定。

每次默认只生产或精修一节。多节任务分别留简报和证据；不把整门课一次生成后视为完成。可直接复制 [单课任务提示词](COURSE_GENERATION_PROMPT.md)。本轮四课示例与尚未完成的审校见 [MA101 编辑审查](MA101_EDITORIAL_REVIEW_V1.md)。

## 开写前：简报、事实和目标任务

1. `git fetch origin main` 后核对 HEAD、远端与工作区；记录实际基线提交，保留已有改动。阅读当前源码、前后节、最新审查和工程指南，不能把旧审查中的问题当成现稿问题。
2. 复制编辑规范的 [课前编辑简报模板](COURSE_EDITORIAL_STANDARD_V1.md#editorial-brief)，保存到本次审查记录。写明目标学习者、先修能力和真实补修链接、一个核心问题、2–4 个可观察目标、主例数值及单位、解释顺序、核心/可选边界、图与代码的任务、未决问题。无需再抄规范全文。
3. 简报旁登记事实来源和校验表。没有来源或没有运行的项目标记“待核”，不得写成已通过。教学构造的数据说明用途，不伪装为实测。事实来源不能只引用写作 AI 的回答。
4. 先手算主例和练习，确定正确图形和代码预期，再起草正文。没有代码的课明确写“不适用”，不为形式增加代码。

来源与可靠性登记可复制此表；关键事实各占一行：

| 事实/资源 | 来源 URL 或仓库路径与提交 | 版本/访问日期 | 具体核对点与独立方法 | 授权/归属与复用方式 | 结论、复核人或待办 |
| --- | --- | --- | --- | --- | --- |
| 待填 | 待填 | 待填 | 不以原答案为预期直接回读 | 区分链接参考、原文/图/代码复用；未确认则写待核 | 待填 |

目标任务表补充简报的 `assessmentMap`，用于检查语义，不再建第二个运行时模型：

| objective（从 1 起）与可观察动作 | 正文教学支点（section.id / 图 / 例子） | 核心 exerciseIds | 学生需独立产生什么 | 两级提示、答案、错法与 rubric 检查 | 待人工复核 |
| --- | --- | --- | --- | --- | --- |
| 待填 | 待填 | 待填 | 计算过程/解释/实现等 | 提示一指思路；提示二给中间步骤；解答解释原因；指出错法及自查依据 | 不以存在映射证明效度 |

`objective` 对应 `Lesson.objectives` 的一基编号；`exerciseIds` 是现有开放练习 ID 数组。普通核心课只能映射到 `tier=core` 的开放题。`lessonSchema` 已校验目标覆盖、未知 ID 和可选层级；人工还须判断“题目是否真的检验这个动词”，不能只检查有关联。需要先修的新概念不能藏在可选区后成为核心题的条件。

## 第一轮：写作与教学编辑

按简报生产 `Lesson` 数据，使用现有 paragraph、math、vector-figure/image、code、exercise 等组件。阅读顺序围绕本节知识安排；问题、数字、符号、任务之间要有解释。H1/H2/H3 使用自然标题，只有真实下级内容才用 H3；目录保留 2.1/2.2 显示号。已有 section、练习、课时 ID 和链接继续可用。

逐段审读并记录原句、位置、疑问和改法：

- 初学者此刻是否已经知道用到的概念和符号？从例子到结论之间是否少了计算或理由？
- 这一段给了新信息吗？对同一个误解的重复提醒是否能合并到首次相关解释？保留必要边界、反例和参考答案中的自查提示。
- 术语、单位、主例和正负方向与前后节是否一致？更换例子时交代变化。
- 标题是否准确指出这段要解决的问题？不为“去模板”统一换词，不按词频、字数、段落数或固定 H2 数判优劣。
- 图前后是否说明看什么和读出什么？代码是否说明运行位置、环境和预期，并在适合时给“先预测、再运行”的输入变化？

有证据才修改。仅重复感或标题通用，不足以认定教学缺陷；记录保留理由。句式对照至少包括原文、学习困难的具体机制、改文和下一步可观察任务，效果只能写“预期，待试学验证”。

## 第二轮：重新求解与技术校验

离开写作轮的结论，从题干、公式定义和图形输入重新求解。可由另一位审阅者复核，也可另开校验轮；同一 AI 换一轮提示仍是工具辅助复核，不属于独立人工审核。记录校验者和方法。

| 对象 | 实际操作 | 现有入口 | 能证明的范围 |
| --- | --- | --- | --- |
| 数学 | 从给定条件逐步手算；检查符号、求和范围、单位、维度、零/负数、假设和所有答案；用不同方法核对 | 严格 KaTeX 解析、`tests/test_math_v2_2.py`、`tests/test_teaching_v2_3.py` 等实际相关测试 | 解析成功仅证明语法；数值检查仅覆盖所测情形 |
| 配图 | 对照输入核查端点、箭头、轴向、等比例、标签、图注与 alt/desc；零向量无方向箭头；检查窄屏可读性 | `vector-teaching.ts`、`vector-figure.tsx`、既有图形测试；PNG 则对应绘图源与数值证据 | 数值正确仍需实页看标签、布局和阅读顺序 |
| 代码与下载 | 实际执行正文；独立预测输出，核对与图/表的对应；有下载时核对同源脚本和空输出 Notebook | `prepare:downloads` → `test:python`、`validate-python.ts` 的独立预期 | 不代表所有 Python/库版本；不能把执行成功当作学生会写 |
| 习题 | 不看解答先做，再核对两级提示、参考答案、常见错法、rubric、核心目标覆盖与新数字 | `lessonSchema`、`assessmentMap`、`review:teaching`、现有 TS 测试 | 自动检查不能判断题目充分性与真实迁移 |
| 工程与导航 | 类型、Lint、单测、构建、生产 HTTP；实测修改页的桌面/移动目录、旧 hash、折叠、提示/答案和前后课 | README 检查命令、`test:routes`、真实浏览器 | 视口模拟不等于实体设备或真实试学 |

复用现有发布清单，不增加 CMS、评分系统、在线 Python 或模型 API。新增数学/代码行为时才补有意义的测试；单纯措辞精修不堆叠逐字断言或大量截图。

## 留存每轮证据

四个现有检查脚本支持 `AIVORA_EVIDENCE_DIR`，默认仍输出原 `docs/TEACHING_V2_3_*` 路径；新一轮应设唯一子目录。文件名沿用原脚本命名，不能据此把新稿称为旧稿。`review:editing` 另支持 `AIVORA_EDITING_BASELINE`，必须在编辑前保存实际基线，不能继续拿 V2.2 快照冒充本轮前稿。

PowerShell 示例（将 `my-lesson-review` 替换为本轮唯一目录名，先保存基线，再编辑）：

```powershell
$env:AIVORA_EVIDENCE_DIR = 'docs/my-lesson-review'
New-Item -ItemType Directory -Path $env:AIVORA_EVIDENCE_DIR -Force | Out-Null
$env:AIVORA_EDITING_BASELINE = "$env:AIVORA_EVIDENCE_DIR/TEACHING_V2_3_BEFORE.json"
npm run review:editing -- --baseline
# 在这里编辑教材；--baseline 采用独占创建，已有快照不会被覆盖。
# 若本轮按工程规则确认内容版本递增，将下一行改为：npm run review:editing -- --allow-version-increase
npm run review:editing
npm run review:teaching
npm run prepare:downloads
npm run test:python
npm run typecheck
npm run lint
npm test
npm run build
# 另一个终端：npm start -- --port 3001
npm run test:routes
Remove-Item Env:AIVORA_EVIDENCE_DIR
Remove-Item Env:AIVORA_EDITING_BASELINE
```

`review:editing` 当前专门导出 MA101 四篇的完整前后文及 ID 兼容结果；其他课程用 `review:teaching` 和 Git diff 留证，不宣称这个脚本覆盖其他课。按 `COURSE_AUTHORING.md` 补齐生产浏览器验收，将实际命令、环境、时间、退出码、失败修复、覆盖与限制写入本轮报告；只保留有助于复核的截图。`prepare:downloads` 会重建资源，检查生成差异，不手改下载文件。

新增核心任务或实质改变达标要求时，先按工程指南决定内容版本并同步清单，保留旧修订记录而不继承新版完成。对比脚本需显式声明 `--allow-version-increase` 才接受递增，仍拒绝倒退与旧锚点丢失。本次三类课的实例见 [跨学科验证](CROSS_DISCIPLINE_EDITORIAL_VALIDATION_V1.md)；V1.1仅为讨论建议，现行教学标准仍是V1.0。

## 人工审稿、试学与发布交接

技术通过后，内容保持 `pending-review/preview`，`technicalEvidence` 指向适用于当前稿件的报告。审稿者亲自确认后才能填 `reviewEvidence` 和变更状态。沿用现有 schema 门禁；维护者还须验证证据内容，不能只填一个非空路径。

复制以下交接表到每轮报告，未完成项保留待办，不代填人名、分数或学生结果：

| 工作 | 责任角色 | 完成证据 | 当前状态 |
| --- | --- | --- | --- |
| 逐课学科审查：事实、定义、推导、边界、图/代码/题目 | 有相应能力且亲自审稿的人，姓名待填写 | 课时 ID、稿件提交、逐项意见、处理决定、签署日期 | 待人工审校 |
| 中文与教学编辑：先修、例子、自然标题、重复、目标任务充分性 | 编辑/教师，姓名待填写 | 精确段落、原句与改法、保留理由、未决项；如用量表逐项给证据 | 待人工审校 |
| 目标学生试学：满足先修但未学过本主题，无人补讲读文后做新题 | 试学组织者与自愿学习者，待安排 | 匿名记录先修、独立过程、卡点、提示使用、解释/答题原稿、阅读/练习/代码分项耗时；说明样本范围 | 未开展 |
| 根据证据修订并决定状态 | 维护者 | 绑定修订提交的技术/人工/试学证据，说明剩余问题；正式发布前审定试学结论 | 待前序工作 |

试学先做不看提示的新任务，再逐级提供提示，保留过程，不把看完答案或手动“读完”当作掌握。若组织者补讲，记录补讲点并区分补讲后的表现。未开展时仅写试学方案；不得生成虚构学生、耗时分布、通过率或效果改善。编辑时间估计暂不依据字数变化调整。

`reviewed/pilot/published` 的技术字段门禁不自动检查真实试学是否充分，正式发布前由维护者核对本表和编辑规范第 13 节；AI 初审、自动测试与浏览器截图均不能替代这些人类证据。
